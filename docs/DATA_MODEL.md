# Data model

This document describes two separate databases. **Everything above [Content Studio schema](#content-studio-schema--the-separate-gcd_studio-database) is the live `gcd-social-db`**, migrated by `src/state/migrate.ts` from `state/migrations/`. The Content Studio's own database, `gcd_studio`, has a different runner, ledger, connection variable and directory, and shares nothing with it; it is described only in that last section.

SQL files under `state/migrations/` are authoritative for the live database. `_migrations` records applied filenames. PostgreSQL is required for runtime durability; API, worker, and scheduler request durable state and probe connectivity, migration-005 approval/media columns, both approval integrity constraints, and all four integrity triggers before starting. In-memory maps remain available only when an offline harness/self-test explicitly initializes without that requirement and cannot authorize publication.

| Table | Purpose | Sensitivity / lifecycle |
|---|---|---|
| `brief_queue` | Input brief, pending/running/done/failed status, claim time, outcome | May contain business strategy, prompts, generated result/provider IDs; no retention/reaper |
| `approval_queue` | Legacy package columns plus immutable typed canonical subject, SHA-256, hash-only decision token, decision/publication expiries, revocation metadata, human decision/status | Unpublished exact provider content and actor labels; URL token is not retained in plaintext after Phase 0A |
| `approval_decisions` | One unique, append-only terminal approve/reject record per approval, including subject type/hash and decision metadata | Security/audit metadata; `decided_by` is a label, not authenticated identity |
| `media` | Generated JPEG bytes plus their SHA-256 | Public content-addressed creative assets; migration 005 blocks id/MIME/bytes/digest changes and every DELETE, so no retention deletion is currently possible |
| `events` | Monotonic live telemetry **and durable worker phase markers** | Mixed criticality: most rows are best-effort telemetry, but `brief:approval_requested`, `brief:publish_attempt_started`, `brief:publish_attempt_settled`, `brief:reconciled_stranded`, and `approval:orphan_revoked` are recovery state (see below); no retention task |
| `session_state` | Arbitrary JSON session state and default Instagram-login token store | Contains the live Instagram-login token and env seed in plaintext when that path is used; critical secret data |
| `brand_scorecard` | Intended quality/performance history | Schema exists; active worker does not write it |
| `self_improvement_proposals` | Intended proposal lineage | Schema exists; active worker does not write it |
| `_migrations` | Applied migration filenames | Operational schema metadata |

## Relationships and invariants

Brief and approval records have no foreign key. Their only link is a worker log line, so no process or operator can tell from the database which approval belongs to which brief. The worker-ownership change (PR #36 — **merged and deployed, its code live in the current `44d7336…` release, independently verified 2026-08-28**; the bootstrap's behavioural evidence remains operator-reported 2026-08-27, not independently re-examined) closes this: `brief:approval_requested` records `{approvalId, packageCount}` against the brief's `run_id`, making that linkage durable. Rows written before that release went live carry no such marker, so the August 10 brief could only be classified from the absence of one. Events correlate by free-text `run_id`.

### Durable phase markers (safety state, not telemetry)

**Merged in PR #36; deployed — the code is live in the current `44d7336…` release, independently verified 2026-08-28.** The bootstrap release's own behavioural evidence remains operator-reported 2026-08-27, not independently re-examined; it required zero pending approvals precisely because no pre-existing row carried these markers — see [Deployment control](DEPLOYMENT.md).

`recordEvent` remains best-effort telemetry whose callers may swallow failures. `recordDurablePhaseEvent` is a separate primitive over the same table whose failure **must** propagate, because interrupted work is classified purely from these rows:

| Marker | Data | Meaning |
|---|---|---|
| `brief:approval_requested` | `approvalId`, `packageCount` | An approval exists and is bound to this brief |
| `brief:publish_attempt_started` | `approvalId`, `packageIndex`, `platform` | Committed **before** the provider request; its presence without a settled or abandoned sibling means the provider outcome is unknown |
| `brief:publish_attempt_settled` | `approvalId`, `packageIndex`, `platform`, `ok`, `providerPostId?`, bounded `error?` | The attempt's outcome is known |
| `brief:publish_attempt_abandoned` | `approvalId`, `packageIndex`, `platform` | Ownership was lost at the pre-request barrier while still held enough to write; positively proves the provider was never contacted |
| `brief:reconciled_stranded` | full recovery outcome | An interrupted brief was terminalized |
| `approval:orphan_revoked` | `approvalId` | A pending approval with no owning brief marker was revoked |

The governing invariant is that **no external side effect may begin unless its preceding marker has durably committed**. A dropped marker would make an already-published brief indistinguishable from one that never reached a provider, so the marker call sites that precede a side effect must never be converted back to the fire-and-forget pattern used elsewhere. Markers are read **by kind**, not as the oldest N events: a chatty run would otherwise truncate its own safety trace into looking like a run that never requested an approval, which is the most dangerous direction to be wrong in. Marker error text is bounded to 300 characters so provider response bodies do not accumulate in durable state.

Worker exclusivity is enforced by a PostgreSQL **session-level advisory lock** on key `(1889446263, 889784911)`, derived from the namespace `gcd-social:worker-ownership:v1` as the first two big-endian int32s of its SHA-256. It is runtime state rather than schema, held on a dedicated client for the worker's lifetime, and released automatically when that session ends. Do not reuse that key for anything else. The `pending → running` claim executes on that same ownership session, so it cannot commit after ownership is lost. A social-post approval subject is a nonempty exact multi-platform `PostPackage[]`; every item must pass strict validation and each platform may appear only once. Each item binds non-secret `target` account/location/host/version fields, and each image binds a public content-addressed URL plus `contentSha256`; credentials/tokens are excluded. Media is referenced without a database foreign key. `approval_decisions.approval_id` has a restrictive foreign key to `approval_queue`. Session state is keyed text and can mix benign state with credentials.

Only a pending, unrevoked approval with a valid unexpired decision token and intact subject hash may transition through the decision function. The PostgreSQL conditional update and unique decision row ensure concurrent/double decisions cannot both win. The browser records `decided_by="human"`, not an authenticated identity. Decision-token and publication-authorization lifetimes are separate and default to 24 hours; revocation blocks pending decisions or a previously approved authorization. There is currently no HTTP revocation route.

Phase 0A canonicalizes the JSON subject by recursively sorting object keys, applies SHA-256 to those bytes, and stores only SHA-256 of the random 32-byte base64url decision token. Migration 005 requires the deprecated plaintext-token column to remain NULL. Whenever a bound Phase0A canonical `subject_payload` is present, the legacy `package`/`package_formatted` copies must also be nonnull and equal to it; revoked/unbound historical rows may retain a NULL subject and are not backfilled into valid approvals. The approval trigger prevents later changes to those subject fields, subject type/hash, token material, and expiry fields; allows only pending→approved/rejected and approved→posted/failed status movement; restricts decision metadata to the terminal human decision; and makes revocation one-way and immutable. Decision rows reject UPDATE/DELETE. Application code validates the complete social-post subject before creation and decision and on every durable load/publication check. At posting entry and again through a module-issued `PublicationGuard.beforeMutation()` immediately before every provider HTTP attempt—including read-only polls, retries, and multi-step writes—it verifies status, matching decision, revocation, authorization expiry, subject type, canonical hash, package index, exact package equality, runtime target parity, and each image's immutable media content/current byte digest plus the 5-MiB/JPEG/allowed-profile policy. Request construction enforces target parity too. Posting status is written after provider calls, but there is no per-platform durable table, idempotency constraint, or reconciliation state machine.

Migration 005 backfills `media.content_sha256` from `media.bytes`, requires lowercase 64-hex digests equal to the stored bytes, and rejects changes to the row id, MIME type, bytes, or digest as well as every DELETE. New media URLs are `/media/<uuid>-<sha256>.jpg`; the older `/media/<uuid>.jpg` route remains read-only for published-link compatibility. This is a deliberate integrity/availability tradeoff: a future retention or deletion policy requires a reviewed forward migration rather than an application cleanup task.

## Migration procedure

Add a lexically ordered SQL file. The runner creates `_migrations`, skips recorded names, and applies each new file in its own transaction. Test against disposable PostgreSQL, inspect data changes/locks, back up production, and deploy compatible code. There is no down migration. **A reversal, where one is planned, is documented SQL under `state/rollback/` and is applied by hand under its own authorization** — it must never be placed in `state/migrations/`, where the forward-only runner would apply it as if it were a forward migration and immediately undo the file before it.

`005_approval_integrity.sql` deliberately revoked every legacy pending/approved row lacking the new canonical hash or token hash, marked why it was revoked, cleared all values from and then constrained the deprecated plaintext `approval_token` column to NULL, and required nonnull equal canonical/legacy copies whenever a bound Phase0A subject exists. It did not backfill unbound historical artifacts into approvals. It also scanned/backfilled the media table and installed approval/decision/media triggers. **Historically**, migration 005's native-auto-deploy rollout raced the worker ahead of the API migration, which is why future migration releases require coordination. **Production was independently observed running `44d7336…` with migrations `001–006` applied on 2026-08-28** — see [Status](STATUS.md) for that dated evidence. The current live release and applied migration set are **`UNKNOWN` unless separately verified**. The Phase 0D controller stops before any deployment when `LIVE_SHA..TARGET_SHA` changes `state/migrations/**`; a separately authorized rollout must assess actual table/media volume and locks, stop worker/scheduler, take a backup, drain or revoke incompatible approvals, use exactly one migration runner/process, start only compatible services after success, and issue fresh approvals where required.

`007_evidence_bounds.sql` is **merged to `main`** through PR #54, and is now **production `APPLIED`**: M1 (an API-only deployment of exact artifact `A` = `d5015236672a02bf8f58d342625c32a4f5acc8a1`) was independently verified 2026-09-18, with `_migrations` recording it applied at `2026-09-17T18:52:22.268131Z` inside that deploy window — see [Status](STATUS.md) for the full record. It is additive: `CHECK` constraints on `content_evidence` and `content_evidence_relations` mirror `EVIDENCE_LIMITS`, applying both character and UTF-8 byte ceilings to text. `detail` uses one compatible contract — at most 4,000 UTF-8 bytes in PostgreSQL's canonical `jsonb::text`; TypeScript computes a conservative upper bound for that same representation, including JSONB's formatting spaces and a 327-byte allowance for the signed finite value `-5e-324`. Tests accept canonical detail at exactly 4,000 bytes, reject 4,001, and reject the exact `{ a: [...Array(12).fill(-5e-324), "x".repeat(53)] }` counterexample for which the former 326-byte numeric allowance estimated exactly 4,000 bytes while PostgreSQL's canonical representation is 4,012 bytes. The tag constraint rejects too many entries, overlong entries, and NULL elements. Its `IMMUTABLE` `STRICT` helper is uniquely named `gcd_content_evidence_tags_within_v007(text[], integer)` and uses plain `CREATE`, never `CREATE OR REPLACE`: a pre-existing exact-name collision aborts migration 007 without overwriting the unrelated function, so the rollback can only remove a helper 007 successfully created. Disposable PostgreSQL 16.15 and 18.6 tests apply and enforce 007, run its documented rollback, reapply it, and prove collision refusal; each version reports 208 checks (fresh 59, upgrade 80, durable 69), including refusal when a direct database row cannot be reconstructed as a valid TypeScript evidence record. Immediate validation remains justified only by the operator's 2026-09-02 aggregate read-only audit finding both tables empty, not by guessed data distributions. The rollback drops each constraint, then the owned helper, and removes 007's `_migrations` row. Applying either file to production remains a separately authorized operator action, and merging 007 to `main` granted no part of that authority: application still requires its own authorization, a fresh read-only production audit confirming the constraint can be validated against the data actually stored, the separately authorized migration-bearing rollout procedure rather than the ordinary controller path, and post-application verification.

## Retention and recovery decisions

Define retention for briefs, approval subjects/token hashes/decision records, events, session state, scorecards, and proposals. Media retention is blocked by the new no-delete trigger and needs a later reviewed migration that preserves published URLs and approval integrity. Encrypt or move provider tokens out of general session JSON. Database restore must be reconciled against external posts and Slack messages after the backup timestamp; restored approval state is rechecked live but cannot prove what a provider already received.

Before Phase 0B, define a separate durable evidence model that distinguishes verified automotive facts, sourced research, GCD direct observations, GCD empirical performance evidence, creative hypotheses, causal hypotheses/inferences, and unsupported assumptions. It should carry source/type/provenance, confidence, freshness, observation/review/expiry timestamps, conflicts, and supersession. See [Roadmap](ROADMAP.md).

## Content evidence (migration 006 — applied to production 2026-08-28)

`content_evidence` and `content_evidence_relations` are the durable substrate for Phase 0B reasoning. **Migration 006 is merged to `main` (`44d7336…`), and was applied to production exactly once as observed on 2026-08-28 — independently verified that date by a separate final-inspection session with read-only PostgreSQL access, which observed the database state at that time and `_migrations` holding six rows with `006` exactly once.** That reading is dated evidence, not a statement about the current contents of `_migrations`. The exact application timestamp (`2026-08-28T15:24:18.56508Z`) and its approximately 53 ms duration are **operator-reported**, not independently re-derived. It was applied to the shared production database by the API pre-deploy runner (operator-reported); the three application services were then separately deployed at the target commit. Both tables were confirmed empty before and after. The rollout stopped once mid-flight, at step 6, under stop conditions S8/S18 because the runbook's index count was wrong (9 vs. the catalog's 10) — the schema itself was always correct. Once the document was corrected, the rollout resumed and completed: the worker and scheduler now also report `44d7336…`. See the [Phase 0B.0 rollout runbook](ROLLOUT_PHASE_0B0.md) for the full record.

**Independently inspected 2026-08-28.** Migration 006 creates 34 catalog objects — 2 tables, 10 indexes (including the 2 primary-key-backed indexes), 16 CHECK constraints, 3 foreign keys, 2 primary-key constraints, and 1 trigger — and is **purely additive**: no `ALTER TABLE`, no `UPDATE`, no `DELETE`, and every foreign key points at a table it creates itself. Measured against disposable PostgreSQL 16, applying it inside a transaction took **no lock of any kind** on `approval_queue`, `approval_decisions`, `media`, `brief_queue`, `events`, or `session_state`, and it completed in about **50 ms**. It therefore cannot block a running worker or scheduler.

A primary key is **two** catalog objects in PostgreSQL — a `pg_constraint` row and the unique index enforcing it — so each of the two primary keys is counted once as an index and once as a primary-key constraint. That is deliberate, and it is why the categories total 34 rather than 32. Counting only the migration's `CREATE INDEX` statements gives 8; the catalog reports 10.

Because the Phase-0A startup probe is existence-scoped — it counts triggers restricted by `tgrelid` to the three Phase-0A tables and constraints restricted by `conrelid` to `approval_queue`, and never reads `_migrations` — code predating this migration runs unaffected against a database that has it. That was **tested, not assumed**: `a6a4316…` was built and its durable startup probe, console snapshot, and event read all succeeded against a runner-migrated `001–006` database. This is what makes rolling application code back while leaving 006 applied a safe recovery, and why no destructive down migration should be written.

| Table | Purpose | Sensitivity |
|---|---|---|
| `content_evidence` | One claim, with its epistemic class, source, provenance, freshness, and lifecycle | No secrets, no customer PII, no raw analytics payloads; `detail` is small structured context only |
| `content_evidence_relations` | `supports` / `conflicts_with` / `supersedes` between claims | Same |

**The database enforces class separation, not just the application.** CHECK constraints reject a verified fact without a checkable `source_ref`, `provenance`, and `reviewed_at`; reject a verified fact sourced from `model_inference` or `unattributed`; require `observed_at` on observations and performance evidence; force `generalizable = false` on both, so an observation can never be stored as a universal rule; forbid a `causal_hypothesis` with confidence 1; and cap `unsupported_assumption` confidence at 0.5. The TypeScript contract in `src/harness/evidence/contract.ts` mirrors these — application validation gives good errors, the database makes the invariant true.

**History is never destroyed.** Correcting a claim inserts a new row and marks the old one `superseded` with a pointer to its successor; it never rewrites the claim text and never deletes. `superseded_by_id` is a restrictive foreign key, self-supersession is rejected, and a superseded row must name its successor. An auditor can always reconstruct what was believed and when.

`attribute` is what makes conflict detection meaningful: two claims about the shop's warranty disagree, while its warranty and its phone number do not.

Writes come only from the explicit operator command `npm run evidence:sync`, which is idempotent — a second run reports zero changes. Nothing writes evidence during application startup, so a deploy can never silently rewrite what the system believes.

## How it is migrated — five separations from the live runner

| | Live database | Studio database |
|---|---|---|
| SQL | `state/migrations/NNN_*.sql` | `studio/migrations/NNNN_*.sql` (`0001_studio_identity_and_tripwire.sql`, `0002_studio_schema.sql`, and since S6.1 `0003_studio_preflight_requests.sql`) |
| Runner | `src/state/migrate.ts` (`npm run migrate`), unchanged | `src/studio/db/migrate.ts` → `runner.ts` (`npm run studio:migrate`) |
| Ledger | `_migrations` (names only) | `studio_schema_migrations`: name **and sha256 of the file's exact bytes**; rows immutable |
| Connection | `DATABASE_URL` | `STUDIO_DATABASE_URL` only; **refused while `DATABASE_URL` is present at all**, before connecting (`SM1`, `SM1a`, `SM2`–`SM2b`) |
| Identity | — | read-only probes before any other statement: `current_database()` is `gcd_studio`; no live-schema table exists in any schema (`LIVE_SCHEMA_TABLES`, checked against the live SQL by `SM6`); a `_migrations` table must carry the tripwire; once the ledger exists, exactly one matching `studio_database_identity` row (`SM4`–`SM4d`, `SM5`, `SP1`, `SP4`–`SP6`) |

- **The tripwire.** Migration 0001 creates a table named `_migrations`, with the live ledger's `name` column carrying `CONSTRAINT studio_tripwire_refuses_live_runner CHECK (false)`. Nothing writes it. **Verified by execution, not assumed** (`SP13`, `SP14`, PostgreSQL 16 and 18): the unchanged live runner against a Studio-migrated database finds `_migrations`, applies `001_init.sql` inside its transaction, fails on its first `INSERT INTO _migrations`, rolls back and exits 1; the catalog, both ledgers and the identity row are byte-for-byte unchanged and no live table exists.
- **The other direction** (`SP4`, `SP5`): the Studio runner against a live-migrated `gcd_studio` is refused (`live-schema`) having sent only read-only `SELECT` probes — no `BEGIN`, lock, DDL or write — and the database is unchanged. A live-migrated database under any other name is refused as `wrong-database` (`SP2`).
- **Each runner on its own database applies and is idempotent** (`SP3` live; `SP8`–`SP10`, `SP15` Studio). Migration 0003 applies on top of a database at 0002 that holds rows, skipping 0001 and 0002 with their recorded sha256 values unchanged, and a further run is idempotent (`SP16`, `SP17`). A recorded file whose bytes changed (`SP11`, `SM3`) or that is missing (`SP12`) is refused before any statement. Each file runs in its own transaction under a Studio-only advisory lock (namespace `gcd-studio:migration-runner:v1`); a runner that loses a race refuses (`concurrent-runner`) rather than apply twice (`SP7`).
- **Each Studio file also refuses by itself** to run outside `gcd_studio` (a `DO` block), whoever runs it.
- `gen_random_uuid()` and `sha256(bytea)` are built into PostgreSQL 13+ and 11+; the Studio schema needs no extension.

## §4 rules that are not the database's to enforce, and who owns each

None of these was moved out of the database silently: each is application-side by its nature, or needs a capability S2 cannot verify, and each is recorded with the PR that owns it.

**Content Studio S3 (2026-10-01, `IMPLEMENTED`, not merged; no migration).** The S3 rows above are implemented by the worker, `src/studio/worker/**`, and proven by its offline suite (`SW…`) and its disposable-PostgreSQL suite (`SWP…`; [Testing](TESTING.md)). It uses the S2 schema unchanged:

- **The overrun acknowledgement** is an audit row: action `spend.overrun_acknowledged`, target `studio_runs` / the run's id, by a user whose role is `owner`. While any `overrun` entry lacks one, the worker refuses every paid request, and `confirmationsLocked` (`spend.ts`, for S6's confirmation transaction) reports confirmations locked. S6's web writes that row on the owner's action.
- **The worker's own audit rows** (`actor_user_id` null): `job.claim`, `job.preflight_refused`, `job.refused` (a queued job whose run is no longer queued, closed unstarted) and `run.finish` (its state, failure class, runner, kind and settlement). `detail` holds ids, states and classes only, never a goal, model text, fact text or a secret.
- **A paid run's request rows** are written `started`, each with its own ceiling, in the transaction that re-checks the reservation, and are committed before the request is sent; a response completes its row. When a run ends, every row still `started` is completed as `failed` with no cost, so `charged_usd` keeps its full ceiling, and the run is settled from their sum (a `release` or an `overrun` entry).
- **Rewritten files.** The library rewrites `resume-meta.json`, `revision-meta.json` and the two field-measurement files during a run, as the CLI overwrites them. `studio_run_artifacts` rows are immutable, so the worker stores those four once, with their final bytes, when the run ends; every other artifact is stored as it is written.
- ~~`studio_findings` is not yet derived; S5, which renders the findings, owns that.~~ *(Content Studio S5, `IMPLEMENTED`, not merged, 2026-10-02: the worker now derives it, with `studio_runs`' `blocking_findings`, `advisory_findings` and `owner_item_findings`, at run end in the artifact flush's transaction, from the run's own stored `06-final-critic.json` by the library's accessors; a malformed artifact writes no row. No schema change: the table, its CHECKs and its trigger are S2's, unchanged. The web reads the rows and never re-derives `owner_item`.)*

**Content Studio S6.1 (2026-10-05, `IMPLEMENTED`, not merged; migration `0003_studio_preflight_requests.sql`).** The owner accepted S6's stop report: S2's schema could not carry the free preflight → quote flow (a preflight job has no parameters; `studio_quotes` holds only `params_sha256` and requires `ceiling_usd > 0`, so it cannot hold a refusal; nothing stores a revise plan). The owner rejected carrying them through the audit log. 0003 adds `studio_preflight_requests` and the helper `studio_is_text_set(text[])`; nothing in 0001 or 0002 changed, so their recorded sha256 values stay valid. **What S6.2 will write:** the web inserts one request beside each `preflight` job it enqueues; the worker updates it once with its outcome. Until S6.2 nothing writes the table, and the worker still closes a preflight job at once as `preflight_not_built`.

- **The canonical parameter form**, verbatim from the migration: `params_sha256` is the lower-case hex SHA-256 of the UTF-8 bytes of the JSON text that JavaScript's `JSON.stringify` produces (no spaces) for an object with exactly these seven keys, in this order: `{"schema":"gcd-studio-preflight-params/1","action":<action>,"goal":<goal>,"platforms":<platforms>,"scopeTags":<scope_tags>,"sourceRunId":<source_run_id>,"factVersionId":<fact_version_id>}` — `<action>` the row's action; `<goal>` its goal exactly as stored (no trimming, case folding or Unicode normalization), or `null`; `<platforms>`, and `<scope_tags>` or `null`, each sorted by JavaScript's default `Array.prototype.sort` (UTF-16 code-unit order, which is `normalizeScopeTags`'s order); the two ids as PostgreSQL prints a `uuid` (lower case, hyphenated), `<source_run_id>` `null` when absent.
- **The goal's length** is checked in characters as PostgreSQL counts them (`char_length`, code points); S6.2's web must count the same way, not by UTF-16 length.
- **Retention (design §4.7, dated note of 2026-10-05):** a request is kept at least 30 days; after that it may be deleted only when no consumed quote depends on it. A request whose quote was consumed is the record of how its run was priced and is kept with the run.

## Recovery

There is no Studio database yet, so nothing to back up or restore; design §4.7's restore drill belongs to O5. There is no down migration: a reversal would be a documented SQL file outside `studio/migrations/`, applied by hand under its own authorization, exactly as the live rule above requires.
