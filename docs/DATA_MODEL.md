# Data model

SQL files under `state/migrations/` are authoritative. `_migrations` records applied filenames. PostgreSQL is required for runtime durability; API, worker, and scheduler request durable state and probe connectivity, migration-005 approval/media columns, both approval integrity constraints, and all four integrity triggers before starting. In-memory maps remain available only when an offline harness/self-test explicitly initializes without that requirement and cannot authorize publication.

| Table | Purpose | Sensitivity / lifecycle |
|---|---|---|
| `brief_queue` | Input brief, pending/running/done/failed status, claim time, outcome | May contain business strategy, prompts, generated result/provider IDs; no retention/reaper |
| `approval_queue` | Legacy package columns plus immutable typed canonical subject, SHA-256, hash-only decision token, decision/publication expiries, revocation metadata, human decision/status | Unpublished exact provider content and actor labels; URL token is not retained in plaintext after Phase 0A |
| `approval_decisions` | One unique, append-only terminal approve/reject record per approval, including subject type/hash and decision metadata | Security/audit metadata; `decided_by` is a label, not authenticated identity |
| `media` | Generated JPEG bytes plus their SHA-256 | Public content-addressed creative assets; migration 005 blocks id/MIME/bytes/digest changes and every DELETE, so no retention deletion is currently possible |
| `events` | Monotonic live telemetry and JSON data | Operational activity; no retention task |
| `session_state` | Arbitrary JSON session state and default Instagram-login token store | Contains the live Instagram-login token and env seed in plaintext when that path is used; critical secret data |
| `brand_scorecard` | Intended quality/performance history | Schema exists; active worker does not write it |
| `self_improvement_proposals` | Intended proposal lineage | Schema exists; active worker does not write it |
| `_migrations` | Applied migration filenames | Operational schema metadata |

## Relationships and invariants

Brief and approval records are related only through worker memory/outcome, not a foreign key. Events correlate by free-text `run_id`. A social-post approval subject is a nonempty exact multi-platform `PostPackage[]`; every item must pass strict validation and each platform may appear only once. Each item binds non-secret `target` account/location/host/version fields, and each image binds a public content-addressed URL plus `contentSha256`; credentials/tokens are excluded. Media is referenced without a database foreign key. `approval_decisions.approval_id` has a restrictive foreign key to `approval_queue`. Session state is keyed text and can mix benign state with credentials.

Only a pending, unrevoked approval with a valid unexpired decision token and intact subject hash may transition through the decision function. The PostgreSQL conditional update and unique decision row ensure concurrent/double decisions cannot both win. The browser records `decided_by="human"`, not an authenticated identity. Decision-token and publication-authorization lifetimes are separate and default to 24 hours; revocation blocks pending decisions or a previously approved authorization. There is currently no HTTP revocation route.

Phase 0A canonicalizes the JSON subject by recursively sorting object keys, applies SHA-256 to those bytes, and stores only SHA-256 of the random 32-byte base64url decision token. Migration 005 requires the deprecated plaintext-token column to remain NULL. Whenever a bound Phase0A canonical `subject_payload` is present, the legacy `package`/`package_formatted` copies must also be nonnull and equal to it; revoked/unbound historical rows may retain a NULL subject and are not backfilled into valid approvals. The approval trigger prevents later changes to those subject fields, subject type/hash, token material, and expiry fields; allows only pending→approved/rejected and approved→posted/failed status movement; restricts decision metadata to the terminal human decision; and makes revocation one-way and immutable. Decision rows reject UPDATE/DELETE. Application code validates the complete social-post subject before creation and decision and on every durable load/publication check. At posting entry and again through a module-issued `PublicationGuard.beforeMutation()` immediately before every provider HTTP attempt—including read-only polls, retries, and multi-step writes—it verifies status, matching decision, revocation, authorization expiry, subject type, canonical hash, package index, exact package equality, runtime target parity, and each image's immutable media content/current byte digest plus the 5-MiB/JPEG/allowed-profile policy. Request construction enforces target parity too. Posting status is written after provider calls, but there is no per-platform durable table, idempotency constraint, or reconciliation state machine.

Migration 005 backfills `media.content_sha256` from `media.bytes`, requires lowercase 64-hex digests equal to the stored bytes, and rejects changes to the row id, MIME type, bytes, or digest as well as every DELETE. New media URLs are `/media/<uuid>-<sha256>.jpg`; the older `/media/<uuid>.jpg` route remains read-only for published-link compatibility. This is a deliberate integrity/availability tradeoff: a future retention or deletion policy requires a reviewed forward migration rather than an application cleanup task.

## Migration procedure

Add a lexically ordered SQL file. The runner creates `_migrations`, skips recorded names, and applies each new file in its own transaction. Test against disposable PostgreSQL, inspect data changes/locks, back up production, and deploy compatible code. There is no down migration.

`005_approval_integrity.sql` deliberately revokes every legacy pending/approved row lacking the new canonical hash or token hash, marks why it was revoked, clears all values from and then constrains the deprecated plaintext `approval_token` column to NULL, and requires nonnull equal canonical/legacy copies whenever a bound Phase0A subject exists. It does not backfill unbound historical artifacts into approvals. It also scans/backfills the media table and installs approval/decision/media triggers. Do not attempt an unsafe approval backfill. Stop the legacy worker/scheduler as a hard pre-migration gate—that binary ignores `revoked_at`—then back up PostgreSQL, drain/reject outstanding reviews, assess actual approval/media volume and scan/lock time, and use exactly one migration runner/process to apply migration 005 while the legacy processes remain stopped. Start only the compatible API/worker/scheduler before issuing fresh approvals. This migration has been authored for local validation only; this repository does not establish that it has run in any shared or production database.

## Retention and recovery decisions

Define retention for briefs, approval subjects/token hashes/decision records, events, session state, scorecards, and proposals. Media retention is blocked by the new no-delete trigger and needs a later reviewed migration that preserves published URLs and approval integrity. Encrypt or move provider tokens out of general session JSON. Database restore must be reconciled against external posts and Slack messages after the backup timestamp; restored approval state is rechecked live but cannot prove what a provider already received.
