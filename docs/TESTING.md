# Testing

Normal validation is offline and must not publish or call production providers.

## Verified Phase 0D evidence

The Phase 0D exact reviewed head and merge CI passed Node 22 offline quality gates, PostgreSQL 16 and 18 integration, AgentShield 1.4.0, and workflow/YAML validation. The executable offline suites reported posting 52, image 10, orchestrator 81, gate 56, and API 51 passing checks; the Render identity/startup suite reports a single invariant-suite PASS. Each disposable PostgreSQL version reported 86 passing integration assertions (fresh 12, upgrade 33, durable 41), and each bound HTTP suite reported 54 passing assertions. These numbers are evidence from the current executable suites, not a promised permanent count.

After the Phase 0D merge, the production workflow's authorization job failed closed because `RENDER_DEPLOY_AUTOMATION_ENABLED=false`, and its deploy job was skipped. That is expected disabled-gate evidence, not a failed application release and not proof that the controller has operated in production. The current Phase 0D commit was separately observed live on all three Render services through the previous native auto-deploy path; API health and worker readiness matched the exact commit. A normal current-SHA scheduler execution remains unobserved.

The self-tests are executable scripts, not a unified test framework:

- `test:posting` validates pure native request builders and strict package/target/full-subject validation, including rejection of empty arrays, malformed siblings, and duplicate platforms. Adversarial exact-payload matcher/approval checks cover fabricated booleans/IDs, an ephemeral approval at the durable publication boundary, wrong index, changed copy/media/CTA/destination, unknown provider-ignored fields, runtime destination mismatch, expiry, and revocation. Module-private mocked-transport probes cover an issued guard's mid-flow revocation recheck, guard execution before every provider attempt (including Instagram status GETs/retries), rejection of a caller-forged native guard before fetch, redirect refusal, and 2xx responses missing provider post IDs. It does not inject a fake provider into the sanctioned publication entrypoint, tamper a stored database subject, or exercise a live durable hosted-media row.
- `test:image` validates fal model routing/request shape and a fake provider.
- `test:orchestrator` validates JSON parsing, formatter → canonical validation → critic ordering, pass/revision/escalation cycles, canonical-fact override resistance while preserving scheduler context, approval-bound destination injection/fail-closed missing target, production rejection of injected runner/resolver/target and vision-inspector seams, trusted fal host/credential/port policy, malformed/garbled/unsafe QC and a Facebook-only critic-requested image revision, normalization to the four feed profiles plus pure input-header/decode checks, Slack-summary mention/link/markup neutralization, explicit language handling, provider-visible hashtag/media/destination constraints, recursive freeze, and that orchestration never invokes posting. It directly exercises the shared publication-media policy with an allowed-profile JPEG plus non-JPEG and over-5-MiB rejection; static source wires that same pure helper into the live guard. Its injected image resolver does not exercise live download or Jimp quality-90 transcode/output-header checks.
- `test:gate` validates the worker delivery requirement for a strict Slack webhook in every environment, production review-origin rules, non-redirecting bounded Slack request shape, an inert code-delimited approval summary whose generated review URL is the only active link, and adversarial escalation goal/reason/run-ID neutralization; exact Instagram host validation; in-memory queue/media-copy compatibility; durable-state/publication refusal; canonical JSON/hash stability; hash-only expiring decision tokens; atomic terminal decisions; authorization expiry/revocation; exact ephemeral subject resolution; and the absence of an autonomy/boolean bypass.
- `test:api` validates shared-secret fail-closed behavior, accepted header forms/query rejection, trigger schema/content-type/body/time bounds, generic limiter bounds, diagnostic operation timeout, strict content-addressed and legacy media-path parsing, and review visibility/validation of hash, destination, digest, token exclusion, and provider fields without starting the API or calling providers.
- `test:render-identity` validates local identity behavior plus exact production full-commit requirements, optional safe Render instance correlation, PostgreSQL-only worker readiness and API health construction, and worker startup ordering. Failed, throwing, or still-pending state/provider initialization and identity failure cannot emit readiness or enter queue consumption.
- `test:postgres` is an opt-in destructive test that requires `PHASE0A_DISPOSABLE_POSTGRES=1` plus a loopback-only `PHASE0A_POSTGRES_ADMIN_URL`. It creates randomly named fresh/upgrade databases, runs the compiled repository migration mechanism (001–005 fresh and 001–004→seed→005 upgrade), exercises the startup probe, SQL invariants, concurrent durable decisions, expiry/revocation, exact-package authorization, immutable content-addressed media, and the sanctioned publication entrypoint with only its provider transport replaced by a counting offline stub, then drops only those owned databases.
- `test:http-e2e` requires a migrated, non-default loopback `DATABASE_URL`. It creates durable approval fixtures, proves the compiled production API exits before binding when Render commit identity is absent, then starts it with a fake 40-character Render commit/instance, a randomized test control token, `API_BIND_HOST=127.0.0.1`, a minimal sanitized environment, and a child fetch-deny preload. Real localhost HTTP/TCP requests cover the exact health service/PostgreSQL/commit identity, route authentication, trigger schema/content/body/time bounds, the global incomplete-header deadline, prompt closure of unauthenticated/invalid-content-type partial-body sockets, durable enqueue, CORS, approval capability/review integrity, token non-echo, and security headers. It never takes an authenticated diagnostic branch.
- `dryrun` starts `dryrun.cli.js`, whose only static dependency is the environment-preparation helper. In simulated mode it deletes the fixed Anthropic/image, Slack/console/database, Meta/Google/GBP credential/ID, provider host/version, model-name, and public-base-URL keys and forces `NODE_ENV=test` before dynamically importing any configuration-bearing dry-run/orchestrator module. Injected canned agent, inspected-image, and dummy publication-target fixtures then keep the run offline. It reaches approval-ready state and builds request shapes without approval, network, or publishing, even when the caller began with `NODE_ENV=production`. `dryrun:live` preserves caller environment and does not use those injected seams.
- `test:deployment-controller` feeds reviewed Render CLI JSON fixtures into the production controller's injected boundaries. It proves literal enable-gate behavior; A-before-B and B-before-A CI completion order; the late current-main/superseded stop; already-current no-deploy; missing/diverged history rejection; exact `LIVE_SHA..TARGET_SHA` migration detection; strict API→worker→scheduler sequencing; and exact health origin/path/identity plus redirect/content/timeout rejection. Health fixtures exercise a real Node 22 byte-stream response, small and exact-4,096-byte success, a canceled one-byte overflow, a lazy synthetic 1-MiB source that supplies only 4,097 bytes, false-small/absent/oversized/malformed Content-Length, multibyte and malformed UTF-8, stream error, abort, and missing/non-byte-stream bodies. The same suite covers Render-CLI-format adjacent/sequential JSON parsing; exact-target worker readiness plus 10-second stabilization; old/missing/malformed/restarted/crash-bearing log rejection; fail-closed Render states; recursive JSON redaction; recognized percent-encoded/mixed and `=>`/`->` fallback forms; and final-summary Markdown/HTML neutralization with bounded output. It invokes neither Render nor a real health URL.
- `check:markdown-links` resolves local Markdown targets offline. `check:env-coverage` compares literal active/test `process.env` reads with `.env.example` while explicitly classifying operating-system-, Render-platform-, and disposable-test-provided variables. `scan:sensitive` inspects tracked active text for high-confidence credential/PII patterns and reports only file, line, and category—not the matched value. These checks need manual triage and do not prove history or external systems contain no secrets.

The in-memory tests do not by themselves verify PostgreSQL concurrency, a live durable hosted-media row/guard query, migration behavior, or HTTP routing. Use the two opt-in integration commands above only against disposable local state. `test:postgres` refuses a non-loopback administrative URL or a run without its explicit destructive-test acknowledgement; `test:http-e2e` refuses a default or non-loopback database. Never point either test at shared or production data. Migration 005 uses a transaction-local 10-second lock deadline and five-minute per-statement deadline; an integration or rollout timeout requires investigation rather than automatic retry.

Offline validation does not verify deployed API authentication/rate distribution, Slack delivery, live model output, real image pixels, public media reachability, provider scopes/tokens, approval-bound account ownership, duplicate prevention, crash recovery, partial publishing, live Render settings, deployment, or external platform behavior.

`dryrun:live`, `/diag/*`, actual API/worker/scheduler processes, shared/production migrations, Slack approval, image generation, and provider calls require explicit authority, an identified non-production environment, controlled test accounts, spend limits, and external reconciliation. There is no provider sandbox assumed by the code. The API/worker/scheduler now require and probe PostgreSQL at startup, so do not launch them with an unidentified `DATABASE_URL`.

Repository validation must also check all Markdown links, active environment reads versus `.env.example`, agent/model/skill loading claims, migration inventory, credential/PII patterns with manual triage, generated/vendor boundaries, whitespace, and the complete diff. The pinned AgentShield scan should run when available, and dependency audit failures caused by unavailable registry/network access must be reported rather than represented as a pass.

## GitHub CI behavior

`.github/workflows/ci.yml` runs on pull requests to `main`, pushes to `main`, and manual diagnostic dispatch. The Node 22 quality job runs the locked install, build/typecheck, six canonical offline self-test commands, simulated dry run, controller fixtures, repository checks, whole-tree whitespace check, and production dependency audit; it never invokes `dryrun:live`. A two-version disposable matrix reuses `test:postgres`, then migrates a dedicated database and runs `test:http-e2e` on PostgreSQL 16 for established compatibility and PostgreSQL 18 for production parity. AgentShield 1.4.0 is a separate required job: a nonzero scan exit fails CI, and its JSON report upload uses `if: always()` so evidence is retained after a scan failure. Workflow validation downloads actionlint 1.7.12 from its pinned release, verifies its archive checksum, runs it against every workflow, and parses checked-in YAML.

CI has no production secrets. Its only database uses loopback credentials inside the disposable runner service, and the HTTP self-test denies outbound fetch. The production deployment workflow triggers only from a successful push-originated `CI` run on `main`; manual CI dispatch cannot deploy. See [Deployment control](DEPLOYMENT.md).
