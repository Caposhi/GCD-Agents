The self-tests are executable scripts, not a unified test framework:

- `test:posting` validates pure native request builders and strict package/target/full-subject validation, including rejection of empty arrays, malformed siblings, and duplicate platforms. Adversarial exact-payload matcher/approval checks cover fabricated booleans/IDs, an ephemeral approval at the durable publication boundary, wrong index, changed copy/media/CTA/destination, unknown provider-ignored fields, runtime destination mismatch, expiry, and revocation. Module-private mocked-transport probes cover an issued guard's mid-flow revocation recheck, guard execution before every provider attempt (including Instagram status GETs/retries), rejection of a caller-forged native guard before fetch, redirect refusal, and 2xx responses missing provider post IDs. It does not inject a fake provider into the sanctioned publication entrypoint, tamper a stored database subject, or exercise a live durable hosted-media row.
- `test:image` validates fal model routing/request shape and a fake provider. It proves the request carries the provider-friendly **source** size rather than the publication size (1080x1350 requests 1024x1280), that every reviewed source mapping has exactly its target aspect ratio, that an unmapped profile falls back to the target itself, and that provider metadata is preserved when present while absent `width`/`height` never fail generation.
- `test:orchestrator` additionally covers publication-media normalization against the August 2026 incident: a raw 896x1120 PNG passes decode safety but is refused as final publication media; 896x1120 and 1024x1280 both normalize to exactly 1080x1350 JPEG by a pure uniform scale; a 1024x1024 render is **refused rather than cropped** and is typed as a deterministic, non-retryable media-contract failure that spends exactly one generation; malformed and oversized inputs are rejected; QC, hosting, and the content digest all operate on the same normalized bytes; and the durable publication guard still rejects any non-profile size, with the four approved profiles unchanged.
- `test:orchestrator` validates JSON parsing, formatter → canonical validation → critic ordering, pass/revision/escalation cycles, canonical-fact override resistance while preserving scheduler context, approval-bound destination injection/fail-closed missing target, production rejection of injected runner/resolver/target and vision-inspector seams, trusted fal host/credential/port policy, malformed/garbled/unsafe QC and a Facebook-only critic-requested image revision, normalization to the four feed profiles plus pure input-header/decode checks, Slack-summary mention/link/markup neutralization, explicit language handling, provider-visible hashtag/media/destination constraints, recursive freeze, and that orchestration never invokes posting. It directly exercises the shared publication-media policy with an allowed-profile JPEG plus non-JPEG and over-5-MiB rejection; static source wires that same pure helper into the live guard. Its injected image resolver does not exercise live download; the Jimp quality-90 transcode and output-header assertions are now exercised directly by the normalization coverage above, against real generated image bytes.
- `test:gate` validates the worker delivery requirement for a strict Slack webhook in every environment, production review-origin rules, non-redirecting bounded Slack request shape, an inert code-delimited approval summary whose generated review URL is the only active link, and adversarial escalation goal/reason/run-ID neutralization; exact Instagram host validation; in-memory queue/media-copy compatibility; durable-state/publication refusal; canonical JSON/hash stability; hash-only expiring decision tokens; atomic terminal decisions; authorization expiry/revocation; exact ephemeral subject resolution; and the absence of an autonomy/boolean bypass.
- `test:api` validates shared-secret fail-closed behavior, accepted header forms/query rejection, trigger schema/content-type/body/time bounds, generic limiter bounds, diagnostic operation timeout, strict content-addressed and legacy media-path parsing, and review visibility/validation of hash, destination, digest, token exclusion, and provider fields without starting the API or calling providers.
- `test:ownership` validates exclusive worker ownership and interrupted-brief recovery offline with injected boundaries: advisory-key stability against its documented namespace, uncontended acquisition, contention in which a second instance acquires only after the holder's session ends, non-blocking `pg_try_advisory_lock` polling rather than one blocking wait, connection-error and heartbeat loss both fencing side effects, the absence of any reconnect/reacquire path, and aborted acquisition closing its dedicated session. It classifies every interruption phase from durable markers, proves partial known publication preserves provider post IDs and is never reported as zero mutation, and proves a fully settled run is reconstructed rather than lost. It proves the audit event is written before the status change, that recovery never writes `pending` and never calls a provider, and that the orphan sweep spares approvals owned by a real brief. For publication it proves the ordering barrier → started marker → provider → settled marker, that a failed started marker makes no provider call at all, that a failed settled marker after provider success becomes a distinct uncertain outcome that stops all remaining platforms, and that ownership lost before or between platforms prevents any further provider contact. Static assertions confirm the worker actually wires these boundaries and that the recovery module imports no provider code.
- `test:ownership` additionally **executes** the worker fencing rules rather than asserting on source text: ownership lost while orchestration is still computing (no approval is ever created), lost before approval creation, lost before credential acquisition (no token call, no provider call), lost after the started marker commits but before the provider boundary (the second barrier blocks the request), and lost between platforms (the next platform is never contacted). It proves a former owner declines every terminal write so it cannot overwrite a successor's recovery, that the owner path still writes both terminal records, that a hung ownership statement is bounded client-side and destroys its socket, that a former owner cannot claim, and that the ownership-loss exit path is nonzero, never releases the lock, and stops the recurring timers that would otherwise keep the process alive. Remaining static checks are import-boundary facts only.
- `test:render-identity` validates local identity behavior plus exact production full-commit requirements, optional safe Render instance correlation, PostgreSQL-only worker readiness and API health construction, and worker startup ordering. Failed, throwing, or still-pending state/provider initialization and identity failure cannot emit readiness or enter queue consumption.
- `test:content-intelligence` validates the Phase 0B.0 evidence contract, evidence pack, approved-facts adapter, agent registry, and the Content Intelligence preview offline, with no database and no provider. It proves the two forbidden promotions are impossible rather than merely discouraged: a hypothesis or performance row can never be returned as a citable fact, and an observation or performance row can never be stored as generalizable. It proves verified kinds are rejected without a checkable source, provenance, and review; that a `causal_hypothesis` cannot assert certainty and an `unsupported_assumption` cannot exceed 0.5 confidence; that stale evidence is separated out rather than silently used; and that conflicting claims are **surfaced as conflicts and excluded from the citable set**, never resolved by picking the newest or highest-confidence row. Conflict keying is on subject **and attribute**, so two claims about the shop's warranty disagree while its warranty and its phone number do not — a regression case covers the earlier defect where subject-only keying made every approved fact conflict with every other. The approved-facts adapter is proven deterministic (same bytes, same ids, same order) and non-mutating, with provenance carrying the exact content sha256. The registry proves all six stages resolve their checked-in assets, that asset paths outside the four allowed roots and any traversal attempt are rejected at registration, and that every stage is `executionEnabled: false`. The preview is proven inert: it produces a stage plan and an evidence summary, and creates no approval, no brief, and no provider call.
- `test:postgres` is an opt-in destructive test that requires `PHASE0A_DISPOSABLE_POSTGRES=1` plus a loopback-only `PHASE0A_POSTGRES_ADMIN_URL`. It creates randomly named fresh/upgrade databases, runs the compiled repository migration mechanism (001–006 fresh and 001–004→seed→005–006 upgrade), exercises the startup probe, SQL invariants, concurrent durable decisions, expiry/revocation, exact-package authorization, immutable content-addressed media, and the sanctioned publication entrypoint with only its provider transport replaced by a counting offline stub, then drops only those owned databases.
- `test:http-e2e` requires a migrated, non-default loopback `DATABASE_URL`. It creates durable approval fixtures, proves the compiled production API exits before binding when Render commit identity is absent, then starts it with a fake 40-character Render commit/instance, a randomized test control token, `API_BIND_HOST=127.0.0.1`, a minimal sanitized environment, and a child fetch-deny preload. Real localhost HTTP/TCP requests cover the exact health service/PostgreSQL/commit identity, route authentication, trigger schema/content/body/time bounds, the global incomplete-header deadline, prompt closure of unauthenticated/invalid-content-type partial-body sockets, durable enqueue, CORS, approval capability/review integrity, token non-echo, and security headers. It also covers `POST /console/content-intelligence/preview` against the real bound server: unauthenticated rejection, content-type rejection, empty-goal and unknown-field rejection, the six-stage plan with execution disabled, the evidence-class summary, and — asserted directly against the database — that a preview creates no approval and no brief and leaks no secret. It never takes an authenticated diagnostic branch.
- `dryrun` starts `dryrun.cli.js`, whose only static dependency is the environment-preparation helper. In simulated mode it deletes the fixed Anthropic/image, Slack/console/database, Meta/Google/GBP credential/ID, provider host/version, model-name, and public-base-URL keys and forces `NODE_ENV=test` before dynamically importing any configuration-bearing dry-run/orchestrator module. Injected canned agent, inspected-image, and dummy publication-target fixtures then keep the run offline. It reaches approval-ready state and builds request shapes without approval, network, or publishing, even when the caller began with `NODE_ENV=production`. `dryrun:live` preserves caller environment and does not use those injected seams.
- `test:deployment-controller` feeds reviewed Render CLI JSON fixtures into the production controller's injected boundaries. It also proves the widened bounded readiness window: readiness arriving around 90 seconds still succeeds, absent readiness still fails closed at the bound, a previous instance's `LIVE_SHA` marker never satisfies the target check, and heavy previous-instance log volume neither hides the target marker nor trips the saturation guard, while a genuinely saturated window at the readiness bound still fails closed. It proves literal enable-gate behavior; A-before-B and B-before-A CI completion order; the late current-main/superseded stop; already-current no-deploy; missing/diverged history rejection; exact `LIVE_SHA..TARGET_SHA` migration detection; strict API→worker→scheduler sequencing; and exact health origin/path/identity plus redirect/content/timeout rejection. Health fixtures exercise a real Node 22 byte-stream response, small and exact-4,096-byte success, a canceled one-byte overflow, a lazy synthetic 1-MiB source that supplies only 4,097 bytes, false-small/absent/oversized/malformed Content-Length, multibyte and malformed UTF-8, stream error, abort, and missing/non-byte-stream bodies. The same suite covers Render-CLI-format adjacent/sequential JSON parsing; exact-target worker readiness plus 10-second stabilization; old/missing/malformed/restarted/crash-bearing log rejection; fail-closed Render states; recursive JSON redaction; recognized percent-encoded/mixed and `=>`/`->` fallback forms; and final-summary Markdown/HTML neutralization with bounded output. It invokes neither Render nor a real health URL.
- `check:markdown-links` resolves local Markdown targets offline. `check:env-coverage` compares literal active/test `process.env` reads with `.env.example` while explicitly classifying operating-system-, Render-platform-, and disposable-test-provided variables. `scan:sensitive` inspects tracked active text for high-confidence credential/PII patterns and reports only file, line, and category—not the matched value. These checks need manual triage and do not prove history or external systems contain no secrets.

The in-memory tests do not by themselves verify PostgreSQL concurrency, a live durable hosted-media row/guard query, migration behavior, or HTTP routing. Use the two opt-in integration commands above only against disposable local state. `test:postgres` refuses a non-loopback administrative URL or a run without its explicit destructive-test acknowledgement; `test:http-e2e` refuses a default or non-loopback database. Never point either test at shared or production data. Migration 005 uses a transaction-local 10-second lock deadline and five-minute per-statement deadline; an integration or rollout timeout requires investigation rather than automatic retry.

Offline validation does not verify deployed API authentication/rate distribution, Slack delivery, live model output, real image pixels, public media reachability, provider scopes/tokens, approval-bound account ownership, duplicate prevention, crash recovery, partial publishing, live Render settings, deployment, or external platform behavior.

`dryrun:live`, `/diag/*`, actual API/worker/scheduler processes, shared/production migrations, Slack approval, image generation, and provider calls require explicit authority, an identified non-production environment, controlled test accounts, spend limits, and external reconciliation. There is no provider sandbox assumed by the code. The API/worker/scheduler now require and probe PostgreSQL at startup, so do not launch them with an unidentified `DATABASE_URL`.

Repository validation must also check all Markdown links, active environment reads versus `.env.example`, agent/model/skill loading claims, migration inventory, credential/PII patterns with manual triage, generated/vendor boundaries, whitespace, and the complete diff. The pinned AgentShield scan should run when available, and dependency audit failures caused by unavailable registry/network access must be reported rather than represented as a pass.

## GitHub CI behavior

`.github/workflows/ci.yml` runs on pull requests to `main`, pushes to `main`, and manual diagnostic dispatch. The Node 22 quality job runs the locked install, build/typecheck, `npm run test:offline` (currently the eight canonical offline self-test commands listed above), simulated dry run, controller fixtures, repository checks, whole-tree whitespace check, and production dependency audit; it never invokes `dryrun:live`. A two-version disposable matrix reuses `test:postgres`, then migrates a dedicated database and runs `test:http-e2e` on PostgreSQL 16 for established compatibility and PostgreSQL 18 for production parity. AgentShield 1.4.0 is a separate required job: a nonzero scan exit fails CI, and its JSON report upload uses `if: always()` so evidence is retained after a scan failure. Workflow validation downloads actionlint 1.7.12 from its pinned release, verifies its archive checksum, runs it against every workflow, and parses checked-in YAML.

CI has no production secrets. Its only database uses loopback credentials inside the disposable runner service, and the HTTP self-test denies outbound fetch. The production deployment workflow triggers only from a successful push-originated `CI` run on `main`; manual CI dispatch cannot deploy. See [Deployment control](DEPLOYMENT.md).
