## Product architecture principle

The destination is the GCD Content Intelligence Platform / Content OS, not merely a scheduler. It should build an organic automotive media engine for qualified reach, followers, repeat viewing, affinity, retention, engagement, GCD authority, and local dominance, with attribution, leads, and revenue optimized later. Humans continue to film; external editing remains the V1 production path.

> Research gives us the prior. GCD empirical performance becomes the posterior.

Agents should reason. Deterministic services should retrieve, validate, mutate, store, enforce, and publish. Evidence collection may be automatic; changes to prompts, skills, production process, agent behavior, or publishing rules remain governed. Automotive truth, safety, privacy, and approval integrity are hard rules. The system must never fabricate diagnosis, failure/repair evidence, customer facts, or shop evidence, and should prefer real GCD evidence over generic decoration.

## Current production architecture

## Runtime ownership

The repository root builds one TypeScript project into `dist/`. Render declares four runtime resources: PostgreSQL, an API service, a worker service, and a daily cron process. The API and worker share PostgreSQL; the scheduler writes only to the brief queue. All three process entry points initialize state with `requireDurable: true`, which requires `DATABASE_URL`, a successful PostgreSQL connectivity query, the migration-005 approval/media columns, both probed approval integrity constraints, and all four approval/media integrity triggers before work begins. In production, the API and worker also require Render's platform-injected full `RENDER_GIT_COMMIT`; `RENDER_INSTANCE_ID` is retained as optional non-secret correlation identity. In-memory state remains an explicit offline harness/self-test path, not a runtime fallback and not a publication authorization source. There is no Redis, message broker, browser application, or standalone MCP server.

`src/api/server.ts` owns HTTP. `src/worker/index.ts` owns the approval-to-publish lifecycle. `src/scheduler/daily.ts` owns the daily enqueue. `src/harness/orchestrator.ts` is the actual manager: deterministic TypeScript, not the dormant master-prompt manager harness. `src/mcp/*` are imported libraries for image and platform APIs.

### Exclusive worker ownership

**Deployed** — the code is live in the current `44d7336…` release, independently verified 2026-08-28. The production-validated behavioral evidence remains **operator-reported 2026-08-27, not independently re-examined**: the operator reports an approximately 58-second ownership wait before readiness on the first protected deploy, which is this design's predicted behaviour under Render's zero-downtime overlap.

Exactly one worker process may execute work, and that exclusivity is established rather than assumed. Render background-worker deploys are zero-downtime: the new instance starts and only about sixty seconds later does the old instance receive SIGTERM, after which it still gets its shutdown grace. Old and new overlap legitimately, so "my process just started" never implies "the running brief is abandoned".

Ownership is a PostgreSQL **session-level advisory lock** on key `(1889446263, 889784911)`, derived from the namespace `gcd-social:worker-ownership:v1`, held on a **dedicated `pg.Client`** for the process lifetime — never through the shared pool, whose connections are returned, reaped, and cannot issue a matching unlock. PostgreSQL releases the lock the instant the owning session ends, so clean exit, SIGKILL, OOM, and host loss are identical and require no TTL. There is deliberately no reconnect-and-reacquire path: by the time a lost session could reconnect, a successor may legitimately hold the lock.

The invariants, each proven by `npm run test:ownership` against injected boundaries:

- **A non-owner does nothing.** A worker that has not acquired the lock reconciles nothing, emits no readiness, and consumes no work. It waits.
- **Recovery runs only after ownership is acquired**, because recovery is destructive. Ownership-loss monitoring starts before recovery, so ownership lost mid-recovery is caught rather than written through.
- **Recovery terminalizes; it never resumes.** Every remaining `running` brief provably has no live owner and is classified from its durable phase markers, then written to a terminal state. Nothing is resumed, retried, or returned to `pending`, and recovery imports no provider code and issues no provider request.
- **The claim itself is fenced.** The `pending → running` transition executes on the ownership session, so it can only commit while this process is still the exclusive owner, and ownership is rechecked after the commit. A dead session cannot commit, which is what makes the invariant hold by construction rather than by timing. The pool-based `claimNextBrief` remains only for the offline/in-memory path and for callers that are not the owning worker.
- **Durable phase markers are safety state, not telemetry.** `brief:approval_requested`, `brief:publish_attempt_started`, `brief:publish_attempt_settled`, and `brief:publish_attempt_abandoned` commit *before* the side effect they describe, through a distinct failure-propagating primitive. `recordEvent` keeps its best-effort telemetry contract unchanged; these must never be converted back to it.
- **Ownership loss fences future side effects and ends the process.** Approval creation, credential acquisition, and every provider attempt — including between platforms — are blocked. A second barrier is taken immediately before each provider request, so ownership lost after the started marker commits still prevents contact. The process exits nonzero for restart: recurring timers and pooled connections would otherwise keep the event loop alive as a healthy-looking worker that never consumes again.
- **Former owners decline terminal writes**, so they cannot overwrite a successor's recovery. Nothing is lost, because settled markers carry every provider post ID and a successor reconstructs the same outcome.

**Readiness now proves four things at once:** durable state initialized, exclusive ownership held, work abandoned by a previous owner reconciled, and mandatory initialization complete. It must never be emitted before ownership and reconciliation succeed.

Ownership is **mutual exclusion, not a fencing token**: if an owner's connection dies while its process lives, PostgreSQL releases the lock and a successor may reconcile concurrently. The Phase 0A publication guard is the actual fence — the successor's revocation makes the old process's next pre-request authorization check fail closed — which narrows exposure to a single already-in-flight HTTP request, itself classified as an uncertain outcome.

**What this does not solve.** Interruption during a provider attempt still leaves an outcome the system cannot resolve by itself. It is surfaced and nothing retries automatically, but provider-level `withRetry` remains an independent path that can reissue a request after an ambiguous network outcome. There is no durable provider operation ledger, no idempotency key, and no provider reconciliation, so duplicate publication remains possible and a human must reconcile against the platform. That work is the first item under Next hardening in [Roadmap](ROADMAP.md).

### Reasoning-stage execution (Phase 0B.1–0B.2) — dormant, not established as deployed

`src/harness/agents/stageExecution.ts` is the reusable boundary through which a registered stage may reach a model. Two stages are built on it: `strategyConcept.ts`, **merged** through PR #42 (merge `8c8bd5b0fd500f9a28247f472fd6626bb05c6ebd`), and `automotiveTruth.ts`, **merged** through PR #44 (merge `52050b4d20d03b5cbaf2a98eaab71b2f77685d80`). Neither is established as deployed or production-validated. Neither is reachable: the worker, scheduler, orchestrator, API, preview, approval, publication, provider, image, Slack, database, and evidence-write paths do not call either executor. Every stage still reports `executionEnabled: false`.

Stage 2 (`automotive-truth`) receives the complete typed Stage 1 output — angle, concept, rationale, hypotheses, assumptions, and all citation arrays — inside one bounded untrusted-data block. It decides what content may assert by building a structural whitelist: a permission is a **binding to an evidence id**, never a sentence. The shared evidence projection exposes each record's authoritative `kind` but not confidence, provenance, reviewer identity, or internal timestamps; the recorded class overrides the model's declaration, and what may be claimed is read back from the records rather than from either stage's prose. It does **not** semantically prove model prose or a restatement true — a language model is not a semantic prover of factual truth here.

The boundary's guarantees, and the reason each exists:

| Guarantee | Why |
|---|---|
| At most one model request; no retry, no repair call | A silent retry turns one budgeted decision into unbounded spend; a repair pass is a second chance to argue into an unsupported claim |
| No tools registered; capabilities closed to what the registry declared | Registration is not permission — a widened capability must be a reviewed code change, not a registry edit |
| Instructions come only from registry assets | There is no way to pass free-form system text through the boundary, so the checked-in prompt is always the contract |
| Untrusted inputs framed as labelled data blocks | A stage that concatenates a goal into its instructions is one brief away from executing whatever the author typed |
| Fail closed on missing credentials, assets, timeout, runner error, or invalid output | Nothing degrades to a partial or best-effort result |
| No logging of prompts, evidence, model text, or secrets | The module writes no log lines at all |

Model selection resolves in `modelPolicy.ts` alone: the registry declares a class (`reasoning-heavy`), the executor names no id, and `deterministic-only` refuses to resolve rather than acquiring a model by default.

Validation is where the epistemic contract is actually enforced. The model's cited ids are bound to the exact evidence section the contract assigns them, so a performance or hypothesis id cannot be returned as a verified fact, and conflicted, stale, or inactive ids are rejected even when the id is real.

### Content Intelligence foundation (Phase 0B.0) — merged and deployed

Additive and inert. It changes no production behavior: the scheduled pipeline below is untouched, and no reasoning stage executes.

**Content evidence.** `src/harness/evidence/` defines a typed contract in which epistemic class is a property of every record rather than a convention. Eight kinds — verified automotive fact, verified business fact, sourced research, GCD direct observation, GCD performance evidence, creative hypothesis, causal hypothesis, unsupported assumption — with per-kind validation, mirrored as CHECK constraints in migration 006 so the invariant survives any writer that bypasses the application layer. Two promotions are impossible by construction: a model-authored hypothesis can never become a verified fact, and a performance measurement can never become automotive or causal truth.

**Evidence pack.** `buildEvidencePack()` groups claims by class and pulls out conflicts and stale material. It **reports conflicts and never resolves them** — choosing the newer or more confident row would manufacture certainty from genuine disagreement — and stale fact-class evidence fails closed out of `allowedFacts`. A conflict is two different claims about the same subject *attribute*; distinct attributes of one subject do not disagree.

**Approved facts stay authoritative.** The adapter is a deterministic projection of `config/approved-facts.json`, carrying provenance and the exact content hash. It creates no second source of truth, and import is an explicit operator command rather than a startup side effect. The live copywriter and critic continue to cite the JSON directly until a later reviewed cutover.

**AgentRegistry.** `src/harness/agents/registry.ts` registers the six target stages with model policy, prompt/skill/reference assets, allowed capabilities, required evidence kinds, input/output validators, and prerequisites. Asset paths are repository-relative and allowlist-rooted; traversal is rejected at registration, and a missing mandatory asset fails loudly rather than silently running a stage without its instructions. `executionEnabled` is `false` on every stage.

**Preview.** `POST /console/content-intelligence/preview`, behind the existing console credential, builds the pack, resolves the stage plan, verifies every asset, and returns structured JSON. It calls no model, image provider, or social platform, creates no approval, and enqueues no brief; `assertPreviewIsInert()` makes that a checked property rather than a promise.

## Delivery control plane

Pull requests and `main` pushes enter `.github/workflows/ci.yml`. A production release can begin only from a successful, push-originated workflow named `CI` on this exact repository's `main`, only after the exact-string repository variable gate is enabled, and only inside the serialized GitHub `production` environment. The triggering run supplies `TARGET_SHA`; no dispatch input or artifact does. After the release concurrency slot has been acquired and `origin/main` refreshed, `scripts/render/deployment-controller.mjs` requires `TARGET_SHA` to equal current main before any Render command. A stale result is reported as superseded with no deployment. The controller then derives the actual API `LIVE_SHA`, verifies both commits in fetched repository history, performs no deployment when all three services already report the target, and checks `LIVE_SHA..TARGET_SHA` for `state/migrations/**` before any deploy. Migration changes stop for a separately controlled rollout. Otherwise it performs API → exact public health → worker → target-bound readiness and stabilization → scheduler → all-service SHA verification, one service at a time. Health must come without redirect from the exact checked-in GCD URL and report the expected service, PostgreSQL state, and `TARGET_SHA`. A present Content-Length is an early rejection hint only; the controller independently counts a nonempty BYOB byte stream into a 4,097-byte buffer, cancels on the one-byte overflow probe, uses fatal UTF-8 decoding, and carries the same 10-second abort through fetch and body read. The worker's single structured ready event is emitted immediately before queue consumption, and the controller then observes bounded logs for 10 seconds before permitting the scheduler. In current production that event follows durable state initialization, exclusive ownership acquisition, and interrupted-work reconciliation, which is why the readiness window is 60 attempts at five-second intervals rather than the original ~55 seconds: readiness cannot appear until the previous instance's session ends. The window was widened, never weakened — exact `TARGET_SHA` equality, instance correlation, malformed-marker rejection, stabilization, crash/restart detection, and fail-closed behaviour at the bound are unchanged, and a previous instance's marker is emitted at `LIVE_SHA` and can never satisfy the target check.

**Independently verified 2026-08-28** by a separate final-inspection session: Render native auto-deploy was off on all three services and the GitHub controller was configured with its repository gate `false`, leaving production in an intentional zero-unattended-authority window. Render CLI is the GitHub machine interface; Render MCP is a read-oriented interactive diagnostic interface unless an operator separately authorizes a write. See [Deployment control](DEPLOYMENT.md).

## Orchestration lifecycle

1. A scheduled or manual brief is persisted in `brief_queue`.
2. A worker atomically claims the oldest pending row and marks it `running` (`FOR UPDATE SKIP LOCKED`). In current production that claim executes on the worker's ownership session, so it can only commit while that process is still the exclusive owner.
3. Code replaces only caller-supplied `approvedFacts` with `config/approved-facts.json`, preserving scheduler-authored context fields such as theme, make, service, and day index. Analytics runs best-effort, then copywriter/image-specification/SEO model calls fan out concurrently against that trusted brief.
4. Code ignores model-authored media URL, QC, and provenance fields. It normalizes the requested shared-feed size to one of `1080x1350`, `1080x1080`, `1200x900`, or `1200x630` (default `1080x1350`), then asks the provider for a **provider-friendly source render at that same aspect ratio** — 1024x1280 for the 4:5 profile — and accepts only a direct HTTPS `fal.media` URL without credentials, fragment, nonstandard port, or redirect. The intermediate download is bounded to 20 MiB and 30 seconds.

   **The provider render is an input, not the artifact.** Two policies apply, and conflating them is what blocked scheduled posting in August 2026: *decode safety* governs bytes we are willing to process (supported format, ≤4,096 px per side, ≤16 million px), while the *publication profile* governs bytes we are willing to publish. A provider-native 896x1120 render, or a PNG returned despite a JPEG request, is a perfectly valid input; neither is publishable until this pipeline produces the exact profile. Providers guarantee composition, not exact publication pixels.

   Normalization is therefore: decode-safety validation → uniform-scale plan → resize → JPEG transcode at deterministic quality 90 → reject output over 5 MiB → assert the exact approved profile. **The only sanctioned transformation is a pure uniform scale.** Cropping and padding are refused rather than unimplemented: cropping a 1:1 render into 4:5 would discard 20% of the frame straight through the headline of a text-bearing brand graphic, and padding would alter the composition under review. Uniformity is enforced literally, by **exact rational aspect equality** (integer cross-multiplication), not a near-ratio tolerance: only exact equality guarantees the horizontal and vertical scale factors are the same number, so a source whose ratio is merely close — 897x1121 against a 4:5 target — fails closed rather than being stretched. Any aspect mismatch is a deterministic media-contract failure and is never retried, because the request is byte-identical on every attempt. Mandatory vision QC then runs on the normalized bytes. The strict QC contract includes transcribed text, garble, unsafe, and issue fields; unsafe covers identifiable people/features, readable plates/VIN/contact/customer documents, unsafe shop practice, and material misrepresentation. Only passing bytes are stored and exposed through an HTTPS `PUBLIC_BASE_URL` as `/media/<uuid>-<sha256>.jpg`; one artifact is shared without separate platform crops, and initial generation plus every critic-requested image revision use this same fail-closed path.
5. On every cycle, the platform formatter runs first. Code then constructs the entire canonical `gcd-final-package/v1`, including exact provider-bound text, already-applied hashtags/truncation, language layout, supported media URL/digest, GBP CTA, and a non-secret destination (`accountId`, optional GBP `locationId`, `apiHost`, `apiVersion`) selected from runtime configuration. Deterministic validation checks review/provider equivalence and platform rules, then the package/provider array is recursively frozen before the critic evaluates that exact final package. The provider array must be nonempty, every item must pass strict package validation, and each platform may appear only once. Instagram requires exactly one image with alt/AI disclosure and 8–15 unique provider-visible hashtags equal to the canonical list; Facebook permits at most two hashtags; GBP permits none and requires explicit language/topic type. Because current native FB/GBP request builders send only the media URL, their provider payloads omit unsupported alt/AI fields while the package-level image record preserves runtime provenance. Tokens never enter the approval subject.
6. A PASS requires both deterministic validation and critic PASS. Actionable findings route back to copy, image, SEO, or formatter; the full formatter → canonical package → validation → critic sequence repeats, up to three cycles. Failure escalates without approval. Any best-effort Slack escalation renders bounded goal/reason/run-ID fields as inert text, neutralizing control characters, links, mentions, and backticks.
7. Before creating a row, the worker validates the approval delivery configuration. Every environment running worker approval delivery requires an exact HTTPS `hooks.slack.com/services/...` webhook; a blank value is valid only for paths that do not run that flow, such as direct offline `createApproval` tests. Production additionally requires `PUBLIC_BASE_URL` to be a public root HTTPS origin. It revalidates the whole subject, canonicalizes the exact `PostPackage[]`, stores it as a typed approval subject with its SHA-256, stores only the SHA-256 of a random decision token, and sends the token-bearing review link to Slack without following redirects. Each model-authored summary line is bounded, sanitized, and then code-delimited so controls, mrkdwn, links/bare domains, mentions, and backticks remain inert; the generated review URL is explicitly labeled authoritative and is the message's sole active link. Delivery is retried with a 10-second timeout per attempt. Failed or uncertain delivery must end in confirmed revocation; if revocation cannot be confirmed after bounded retries, a composite error exposes both failures for reconciliation and no approval handle is returned. Decision and publication authorization expire after 24 hours by default. At most one pending decision wins the atomic database transition, and decision handling revalidates the entire subject.
8. After approval, the worker reloads the stored provider array; no content transformation follows. The posting library requires the whole subject to remain nonempty, strict-valid, and unique by platform, rechecks current durable approval/hash/decision/type/status/expiry/revocation/index/exact payload at entry, and passes a frozen stored clone plus a module-issued exact-package guard to the native provider; a caller-created no-op guard is rejected. Every admissible provider awaits that guard immediately before every provider HTTP attempt, inside every read, retry, poll, and multi-step flow. The guard repeats the whole-subject and approval checks, revalidates runtime credentials/configuration against the approved account/location/host/version, and verifies every content-addressed media reference against the database's immutable content fields/current byte digest plus the 5-MiB/JPEG/allowed-profile policy; request construction enforces the same target match. Native requests refuse redirects and require a provider post ID for publication success.
9. The worker records final brief/approval status and telemetry. In current production, durable phase markers commit before each side effect throughout steps 7–8 — approval requested, publish attempt started, settled, or abandoned — and every terminal write is declined if this process is no longer the exclusive owner, so it cannot overwrite a successor's recovery.

## Prompt and skill reality

The orchestrator loads each `agents/<name>.md`, strips YAML frontmatter, extracts only `model`, and sends the Markdown body plus JSON input to Anthropic. Frontmatter `tools` is not enforced. Agent text says to load skills, but the SDK call registers no tools and does not append `skills/*` content. Skills remain authoritative human specifications only to the extent their rules are repeated in the actual agent body or code.

`prompts/MASTER_PROMPT.md` is loaded only by `runManagerTurn` in `agentLoop.ts`, which has no package script or worker caller. The production worker does not invoke an Opus manager agent. Autonomy phases B/C and self-improvement are therefore partial scaffolding rather than complete runtime features.

The earlier research named roughly 22 conceptual specialists. That is not a requirement for 22 production model calls. Phase 0B should converge on about six primary reasoning stages:

2. automotive-truth;
3. hook-story-script;
4. production-direction;

## Trust boundaries

- Human approval: possession of a transitional token-bearing URL; only the token hash is stored, but there is still no user identity/session. UUID-shaped review/decision routes consume both a fixed-window process-local 300/minute direct-socket bucket and a 30/minute direct-socket-plus-approval-UUID bucket. A programmatic revocation primitive exists; no HTTP revocation UI exists.
- Manual intake, diagnostics, and console: one transitional `CONSOLE_TOKEN`, accepted only as `Authorization: Bearer` or `x-console-token`. Missing configuration fails closed. Fixed-window process-local limits are 5/minute for triggers, 20/minute for diagnostics, 120/minute for console, and 60/minute for failed authentication. Query credentials and wildcard CORS are not accepted. Every limiter uses the direct socket address and can become service-wide behind an unconfigured proxy.
- Request bounds: the HTTP server applies 10-second header and complete-request receive deadlines, checked at one-second intervals. Trigger and approval-decision bodies are independently limited to 16 KiB and a 10-second route read; early body-bearing authentication/content-type rejections close their socket without draining unread bytes. Trigger input is JSON-only and contains only a nonempty `goal` of at most 2,000 characters. Diagnostic observation is bounded to 15 seconds, with 10-second Graph fetch aborts.
- Providers: OAuth/API tokens come from environment. On the default Instagram-login path, the live token and env seed are also stored in plaintext PostgreSQL session state; the alternate Facebook-login host remains environment-managed. The worker runs the periodic Instagram token job only when Instagram is active, and post-approval Instagram/Google token acquisition only when the exact approved array contains Instagram/GBP respectively.
- Models/image provider: brief, approved facts, generated copy, prompts, and images leave the system.
- Public media: new generated JPEGs are intentionally unauthenticated, content-addressed by UUID plus SHA-256, and cached for one year with a digest ETag. The legacy UUID-only route remains readable for already-published links. Migration 005 makes every media row's id/MIME/bytes/digest immutable and forbids every deletion; this preserves approved bytes at the cost of requiring a future reviewed migration for retention.

## Invariants and gaps

- An empty subject, malformed or duplicate-platform sibling, unapproved/rejected/expired/revoked/wrong-type subject, wrong index, hash mismatch, or content mismatch must never reach a provider call. The complete social-post subject is validated before creation and decision, on durable load, and again at publication entry/every provider attempt. This invariant applies to all parsed autonomy phases; a boolean cannot stand in for an approval.
- A human approval applies to one immutable, canonical provider payload array, including destination and media digest. Any externally visible change, including target account/location/host/version, requires a new approval; rotating a token without changing that destination does not change the subject. Database triggers prevent mutation of subject/hash/token-lifetime fields and make revocation/decision metadata monotonic.
- External payloads/briefs are data, not instructions.
- Telemetry failures must not break orchestration.
- Model-authored facts/media/provenance are untrusted. Only checked-in facts and runtime-generated, inspected media may enter the current final package. Phase 0B.0 adds source/confidence/freshness/review metadata and evidence constraints, but the production reasoning path still cites the checked-in fact file directly; moving it onto the evidence substrate requires a later reviewed cutover. Detected text/privacy/safety/material-integrity defects, QC infrastructure failures, and malformed QC output fail closed.
- Production orchestration refuses caller-injected agent, image-resolution, publication-target, and vision-inspection implementations. These injectable seams are test-only; simulated dry-run forces `NODE_ENV=test` before dynamically importing configuration-bearing modules.
- Native publishing has no durable idempotency key or provider-operation ledger; exactly-once behavior is not guaranteed.
- **Current production** claims briefs through the exclusive ownership session described above, and startup recovery reconciles anything left `running` by a departed owner: the earlier stranding failure mode, in which a claimed brief had no owner predicate and nothing reclaimed it, no longer describes production. A time-based lease or reaper was rejected rather than deferred, because a brief legitimately stays `running` for up to 24 hours awaiting a human, so no TTL can distinguish a crash from a wait.
- The control-plane shared secret, approval URL transport, in-process rate limiting, missing reviewer identity, and plaintext Instagram token remain transitional risks.

## Phase 0A migration boundary

`state/migrations/005_approval_integrity.sql` is additive to the existing schema. It adds the canonical subject, payload/token hashes, expiry/revocation metadata, a unique append-only decision record, guarded status transitions, and immutable approval metadata. It requires the deprecated plaintext `approval_token` to remain NULL and, whenever a bound Phase0A subject exists, requires nonnull mutually equal legacy/canonical subject copies; unbound historical artifacts are not backfilled into approvals. It also adds and backfills `media.content_sha256`, verifies the digest against `media.bytes`, blocks changes to media id/MIME/bytes/digest, and rejects every media deletion. It deliberately revoked legacy pending or approved rows that lacked the stronger binding and cleared existing plaintext token values. The runner holds each file in one transaction; migration 005 uses transaction-local 10-second lock acquisition and five-minute per-statement deadlines so contention or an unexpectedly large scan fails pre-deploy rather than waiting indefinitely.

Production discovery confirmed the compatible Phase 0A commit live, but the worker began before migration completion because native service deploys raced. For every future migration, the Phase 0D controller stops before API deployment; a separately authorized rollout must back up PostgreSQL, drain/reject incompatible approvals when required, keep incompatible consumers stopped, assess data/locks, and use exactly one migration runner before starting the compatible API/worker/scheduler. Investigate a timeout or partial rollout instead of retrying automatically.
