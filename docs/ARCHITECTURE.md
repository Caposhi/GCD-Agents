# Architecture

Verified against source plus read-only GitHub and Render state on 2026-08-24. Phase 0A and Phase 0D are both deployed at `10098de73667797120da8c7dfa4da83f336ff6ba`. Phase 0B has not begun.

## Product architecture principle

The destination is the GCD Content Intelligence Platform / Content OS, not merely a scheduler. It should build an organic automotive media engine for qualified reach, followers, repeat viewing, affinity, retention, engagement, GCD authority, and local dominance, with attribution, leads, and revenue optimized later. Humans continue to film; external editing remains the V1 production path.

> Research gives us the prior. GCD empirical performance becomes the posterior.

Agents should reason. Deterministic services should retrieve, validate, mutate, store, enforce, and publish. Evidence collection may be automatic; changes to prompts, skills, production process, agent behavior, or publishing rules remain governed. Automotive truth, safety, privacy, and approval integrity are hard rules. The system must never fabricate diagnosis, failure/repair evidence, customer facts, or shop evidence, and should prefer real GCD evidence over generic decoration.

## Current production architecture

## Runtime ownership

The repository root builds one TypeScript project into `dist/`. Render declares four runtime resources: PostgreSQL, an API service, a worker service, and a daily cron process. The API and worker share PostgreSQL; the scheduler writes only to the brief queue. All three process entry points initialize state with `requireDurable: true`, which requires `DATABASE_URL`, a successful PostgreSQL connectivity query, the migration-005 approval/media columns, both probed approval integrity constraints, and all four approval/media integrity triggers before work begins. In production, the API and worker also require Render's platform-injected full `RENDER_GIT_COMMIT`; `RENDER_INSTANCE_ID` is retained as optional non-secret correlation identity. In-memory state remains an explicit offline harness/self-test path, not a runtime fallback and not a publication authorization source. There is no Redis, message broker, browser application, or standalone MCP server.

`src/api/server.ts` owns HTTP. `src/worker/index.ts` owns the approval-to-publish lifecycle. `src/scheduler/daily.ts` owns the daily enqueue. `src/harness/orchestrator.ts` is the actual manager: deterministic TypeScript, not the dormant master-prompt manager harness. `src/mcp/*` are imported libraries for image and platform APIs.

## Delivery control plane

Pull requests and `main` pushes enter `.github/workflows/ci.yml`. A production release can begin only from a successful, push-originated workflow named `CI` on this exact repository's `main`, only after the exact-string repository variable gate is enabled, and only inside the serialized GitHub `production` environment. The triggering run supplies `TARGET_SHA`; no dispatch input or artifact does. After the release concurrency slot has been acquired and `origin/main` refreshed, `scripts/render/deployment-controller.mjs` requires `TARGET_SHA` to equal current main before any Render command. A stale result is reported as superseded with no deployment. The controller then derives the actual API `LIVE_SHA`, verifies both commits in fetched repository history, performs no deployment when all three services already report the target, and checks `LIVE_SHA..TARGET_SHA` for `state/migrations/**` before any deploy. Migration changes stop for a separately controlled rollout. Otherwise it performs API → exact public health → worker → target-bound readiness and stabilization → scheduler → all-service SHA verification, one service at a time. Health must come without redirect from the exact checked-in GCD URL and report the expected service, PostgreSQL state, and `TARGET_SHA`. A present Content-Length is an early rejection hint only; the controller independently counts a nonempty BYOB byte stream into a 4,097-byte buffer, cancels on the one-byte overflow probe, uses fatal UTF-8 decoding, and carries the same 10-second abort through fetch and body read. The worker's single structured ready event is emitted immediately before queue consumption after durable state and required initialization, and the controller then observes bounded logs for 10 seconds before permitting the scheduler.

Native Render auto-deploy is off on all three services. The GitHub controller is configured but its repository gate is false, so production is intentionally in a zero-unattended-authority window. Render CLI is the GitHub machine interface; Render MCP is a read-oriented interactive diagnostic interface unless an operator separately authorizes a write. See [Deployment control](DEPLOYMENT.md).

## Orchestration lifecycle

1. A scheduled or manual brief is persisted in `brief_queue`.
2. A worker atomically claims the oldest pending row and marks it `running`.
3. Code replaces only caller-supplied `approvedFacts` with `config/approved-facts.json`, preserving scheduler-authored context fields such as theme, make, service, and day index. Analytics runs best-effort, then copywriter/image-specification/SEO model calls fan out concurrently against that trusted brief.
4. Code ignores model-authored media URL, QC, and provenance fields. It normalizes the requested shared-feed size to one of `1080x1350`, `1080x1080`, `1200x900`, or `1200x630` (default `1080x1350`), invokes the configured fal adapter, and accepts only a direct HTTPS `fal.media` URL without credentials, fragment, nonstandard port, or redirect. The intermediate download is bounded to 20 MiB and 30 seconds. Before decode, the PNG/JPEG header must use an allowed profile and exactly equal the requested dimensions; broader safety ceilings are 4,096 pixels per side and 16 million total. Runtime transcodes at deterministic JPEG quality 90, rejects output over 5 MiB, revalidates the output header against that same profile before storage/hash binding, and runs mandatory vision QC. The strict QC contract includes transcribed text, garble, unsafe, and issue fields; unsafe covers identifiable people/features, readable plates/VIN/contact/customer documents, unsafe shop practice, and material misrepresentation. Only passing bytes are stored and exposed through an HTTPS `PUBLIC_BASE_URL` as `/media/<uuid>-<sha256>.jpg`; one artifact is shared without separate platform crops, and initial generation plus every critic-requested image revision use this same fail-closed path.
5. On every cycle, the platform formatter runs first. Code then constructs the entire canonical `gcd-final-package/v1`, including exact provider-bound text, already-applied hashtags/truncation, language layout, supported media URL/digest, GBP CTA, and a non-secret destination (`accountId`, optional GBP `locationId`, `apiHost`, `apiVersion`) selected from runtime configuration. Deterministic validation checks review/provider equivalence and platform rules, then the package/provider array is recursively frozen before the critic evaluates that exact final package. The provider array must be nonempty, every item must pass strict package validation, and each platform may appear only once. Instagram requires exactly one image with alt/AI disclosure and 8–15 unique provider-visible hashtags equal to the canonical list; Facebook permits at most two hashtags; GBP permits none and requires explicit language/topic type. Because current native FB/GBP request builders send only the media URL, their provider payloads omit unsupported alt/AI fields while the package-level image record preserves runtime provenance. Tokens never enter the approval subject.
6. A PASS requires both deterministic validation and critic PASS. Actionable findings route back to copy, image, SEO, or formatter; the full formatter → canonical package → validation → critic sequence repeats, up to three cycles. Failure escalates without approval. Any best-effort Slack escalation renders bounded goal/reason/run-ID fields as inert text, neutralizing control characters, links, mentions, and backticks.
7. Before creating a row, the worker validates the approval delivery configuration. Every environment running worker approval delivery requires an exact HTTPS `hooks.slack.com/services/...` webhook; a blank value is valid only for paths that do not run that flow, such as direct offline `createApproval` tests. Production additionally requires `PUBLIC_BASE_URL` to be a public root HTTPS origin. It revalidates the whole subject, canonicalizes the exact `PostPackage[]`, stores it as a typed approval subject with its SHA-256, stores only the SHA-256 of a random decision token, and sends the token-bearing review link to Slack without following redirects. Each model-authored summary line is bounded, sanitized, and then code-delimited so controls, mrkdwn, links/bare domains, mentions, and backticks remain inert; the generated review URL is explicitly labeled authoritative and is the message's sole active link. Delivery is retried with a 10-second timeout per attempt. Failed or uncertain delivery must end in confirmed revocation; if revocation cannot be confirmed after bounded retries, a composite error exposes both failures for reconciliation and no approval handle is returned. Decision and publication authorization expire after 24 hours by default. At most one pending decision wins the atomic database transition, and decision handling revalidates the entire subject.
8. After approval, the worker reloads the stored provider array; no content transformation follows. The posting library requires the whole subject to remain nonempty, strict-valid, and unique by platform, rechecks current durable approval/hash/decision/type/status/expiry/revocation/index/exact payload at entry, and passes a frozen stored clone plus a module-issued exact-package guard to the native provider; a caller-created no-op guard is rejected. Every admissible provider awaits that guard immediately before every provider HTTP attempt, inside every read, retry, poll, and multi-step flow. The guard repeats the whole-subject and approval checks, revalidates runtime credentials/configuration against the approved account/location/host/version, and verifies every content-addressed media reference against the database's immutable content fields/current byte digest plus the 5-MiB/JPEG/allowed-profile policy; request construction enforces the same target match. Native requests refuse redirects and require a provider post ID for publication success.
9. The worker records final brief/approval status and telemetry.

## Prompt and skill reality

The orchestrator loads each `agents/<name>.md`, strips YAML frontmatter, extracts only `model`, and sends the Markdown body plus JSON input to Anthropic. Frontmatter `tools` is not enforced. Agent text says to load skills, but the SDK call registers no tools and does not append `skills/*` content. Skills remain authoritative human specifications only to the extent their rules are repeated in the actual agent body or code.

`prompts/MASTER_PROMPT.md` is loaded only by `runManagerTurn` in `agentLoop.ts`, which has no package script or worker caller. The production worker does not invoke an Opus manager agent. Autonomy phases B/C and self-improvement are therefore partial scaffolding rather than complete runtime features.

## Target Content Intelligence architecture

The earlier research named roughly 22 conceptual specialists. That is not a requirement for 22 production model calls. Phase 0B should converge on about six primary reasoning stages:

1. strategy-concept;
2. automotive-truth;
3. hook-story-script;
4. production-direction;
5. packaging-adaptation; and
6. final-critic.

Other specialists should generally become deterministic services, policy/rule modules, reference material, or optional invocations. Science and evidence should be represented deterministically where possible. Phase 0B must add an `AgentRegistry`, real skill/reference injection, research/reference retrieval, deterministic validation around every agent output, and structured evidence capture. None of those target components is implemented today.

Before that expansion, define the fact/evidence contract described in [Roadmap](ROADMAP.md). A content-performance correlation must never become an automotive fact or causal truth merely because it performed well.

## Trust boundaries

- Human approval: possession of a transitional token-bearing URL; only the token hash is stored, but there is still no user identity/session. UUID-shaped review/decision routes consume both a fixed-window process-local 300/minute direct-socket bucket and a 30/minute direct-socket-plus-approval-UUID bucket. A programmatic revocation primitive exists; no HTTP revocation UI exists.
- Manual intake, diagnostics, and console: one transitional `CONSOLE_TOKEN`, accepted only as `Authorization: Bearer` or `x-console-token`. Missing configuration fails closed. Fixed-window process-local limits are 5/minute for triggers, 20/minute for diagnostics, 120/minute for console, and 60/minute for failed authentication. Query credentials and wildcard CORS are not accepted. Every limiter uses the direct socket address and can become service-wide behind an unconfigured proxy.
- Request bounds: the HTTP server applies 10-second header and complete-request receive deadlines, checked at one-second intervals. Trigger and approval-decision bodies are independently limited to 16 KiB and a 10-second route read; early body-bearing authentication/content-type rejections close their socket without draining unread bytes. Trigger input is JSON-only and contains only a nonempty `goal` of at most 2,000 characters. Diagnostic observation is bounded to 15 seconds, with 10-second Graph fetch aborts.
- Providers: OAuth/API tokens come from environment. On the default Instagram-login path, the live token and env seed are also stored in plaintext PostgreSQL session state; the alternate Facebook-login host remains environment-managed. The worker runs the periodic Instagram token job only when Instagram is active, and post-approval Instagram/Google token acquisition only when the exact approved array contains Instagram/GBP respectively.
- Models/image provider: brief, approved facts, generated copy, prompts, and images leave the system.
- Public media: new generated JPEGs are intentionally unauthenticated, content-addressed by UUID plus SHA-256, and cached for one year with a digest ETag. The legacy UUID-only route remains readable for already-published links. Migration 005 makes every media row's id/MIME/bytes/digest immutable and forbids every deletion; this preserves approved bytes at the cost of requiring a future reviewed migration for retention.

## Invariants and gaps

- An empty subject, malformed or duplicate-platform sibling, unapproved/rejected/expired/revoked/wrong-type subject, wrong index, hash mismatch, or content mismatch must never reach a provider call. The complete social-post subject is validated before creation and decision, on durable load, and again at publication entry/every provider attempt. This invariant applies to all parsed autonomy phases; a boolean cannot stand in for an approval.
- A human approval applies to one immutable, canonical provider payload array, including destination and media digest. Any externally visible change, including target account/location/host/version, requires a new approval; rotating a token without changing that destination does not change the subject. Database triggers prevent mutation of subject/hash/token-lifetime fields and make revocation/decision metadata monotonic.
- External payloads/briefs are data, not instructions.
- Telemetry failures must not break orchestration.
- Model-authored facts/media/provenance are untrusted. Only checked-in facts and runtime-generated, inspected media may enter the final package. Phase 0A makes the checked-in set authoritative against caller override but does not attach or validate source/confidence/freshness/last-review metadata; that research-reference contract is a required pre-0B decision. Detected text/privacy/safety/material-integrity defects, QC infrastructure failures, and malformed QC output fail closed.
- Production orchestration refuses caller-injected agent, image-resolution, publication-target, and vision-inspection implementations. These injectable seams are test-only; simulated dry-run forces `NODE_ENV=test` before dynamically importing configuration-bearing modules.
- Native publishing has no durable idempotency key or provider-operation ledger; exactly-once behavior is not guaranteed.
- Claimed briefs have no lease/reaper; a crash can strand `running` rows.
- The control-plane shared secret, approval URL transport, in-process rate limiting, missing reviewer identity, and plaintext Instagram token remain transitional risks.

## Phase 0A migration boundary

`state/migrations/005_approval_integrity.sql` is additive to the existing schema. It adds the canonical subject, payload/token hashes, expiry/revocation metadata, a unique append-only decision record, guarded status transitions, and immutable approval metadata. It requires the deprecated plaintext `approval_token` to remain NULL and, whenever a bound Phase0A subject exists, requires nonnull mutually equal legacy/canonical subject copies; unbound historical artifacts are not backfilled into approvals. It also adds and backfills `media.content_sha256`, verifies the digest against `media.bytes`, blocks changes to media id/MIME/bytes/digest, and rejects every media deletion. It deliberately revoked legacy pending or approved rows that lacked the stronger binding and cleared existing plaintext token values. The runner holds each file in one transaction; migration 005 uses transaction-local 10-second lock acquisition and five-minute per-statement deadlines so contention or an unexpectedly large scan fails pre-deploy rather than waiting indefinitely.

Production discovery confirmed the compatible Phase 0A commit live, but the worker began before migration completion because native service deploys raced. For every future migration, the Phase 0D controller stops before API deployment; a separately authorized rollout must back up PostgreSQL, drain/reject incompatible approvals when required, keep incompatible consumers stopped, assess data/locks, and use exactly one migration runner before starting the compatible API/worker/scheduler. Investigate a timeout or partial rollout instead of retrying automatically.
