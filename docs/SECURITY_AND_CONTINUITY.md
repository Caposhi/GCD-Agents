# Security and continuity

## Current trust findings

- `/triggers`, `/diag/ig`, `/diag/gbp`, and `/console/*` now fail closed unless the same transitional `CONSOLE_TOKEN` is supplied as `Authorization: Bearer` or `x-console-token`. Query credentials and wildcard CORS were removed. The fixed-window limits are in-process and keyed by direct socket address, so they are neither distributed nor user-aware and may become service-wide behind a proxy.
- Trigger input is restricted to an exact bounded `goal` object. Caller-supplied `approvedFacts` and unknown fields are rejected, and the orchestrator independently replaces any internally supplied facts with the checked-in canonical file.
- Header receipt and the complete HTTP request receive phase use 10-second deadlines checked at one-second intervals. Trigger/approval body readers independently enforce 16-KiB/10-second bounds, while early body-bearing authentication or content-type rejections close the socket without draining unread bytes.
- Approval remains a token-bearing URL transported through Slack/browser history. PostgreSQL stores only the token's SHA-256, and the decision token expires, but there is still no authenticated approver identity or safer review session. UUID-shaped review/decision requests consume a process-local 300/minute direct-socket bucket plus a 30/minute direct-socket-plus-approval-UUID bucket; neither is distributed or identity-aware, and the global bucket can become service-wide behind a proxy.
- Every environment running worker approval delivery requires a validated exact HTTPS `hooks.slack.com/services/...` webhook before approval creation; blank is valid only when that flow is not run, such as direct offline `createApproval` tests. Production additionally validates a public root HTTPS review origin. Delivery refuses redirects and uses bounded retry with a 10-second timeout per attempt. Failed/uncertain notification triggers bounded revocation and must end in confirmed revocation; inability to confirm raises a composite error for reconciliation and returns no approval handle. Escalation notifications remain best-effort and do not grant authorization.
- Slack package summaries are model-influenced previews. Each line is bounded, sanitized, and then code-delimited so controls, mrkdwn, links/bare domains, mentions, and backticks remain inert. The separately generated URL is labeled as the authoritative exact-payload review and is the message's sole active link; operators must decide from that hash-verified page, not preview text. Best-effort escalation messages apply bounded inert-text treatment to trigger/model-authored goal, reason, and run ID.
- Approval authorization is bound to the canonical SHA-256 of the immutable exact provider array, including destination and media digest. The complete social-post subject must be nonempty, strict-valid item by item, and unique by platform; code enforces that before creation and decision, on durable load, and throughout publication. Status, matching durable decision, subject type, authorization expiry, revocation, index, exact payload, runtime account/location/host/version parity, and live immutable media bytes are checked through a module-issued `PublicationGuard.beforeMutation()` immediately before every provider HTTP attempt, including read-only status polls and all retries/multi-step requests. The callback name is transitional; its boundary is all provider I/O. A caller-forged/no-op guard is rejected; a provider that does not await the issued guard at every request is inadmissible. Request construction also enforces target parity. All native provider requests refuse redirects, and a 2xx publication response without a post ID is failure. There is no autonomy/boolean bypass. The revocation primitive has no HTTP/operator UI.
- The default Instagram-login token and original environment seed are persisted plaintext in `session_state`; the alternate Facebook-login token remains environment-managed and is not refreshed by this module.
- The worker avoids unrelated refresh calls: its Instagram refresh timer starts only when Instagram is active, and post-approval Instagram/Google token acquisition is gated by the exact approved platforms. This reduces credential-bound calls but does not isolate or encrypt the environment credential object.
- Credential-bearing native provider requests, Meta/Google diagnostics, Instagram refresh, Google OAuth exchange, and Slack requests refuse redirects. Instagram host selection is exact-allowlisted to `graph.instagram.com` or `graph.facebook.com`; other provider endpoints are fixed/validated by their call sites. This reduces credential replay risk but does not verify external provider ownership or behavior.
- Provider errors may include response text in logs/database outcomes. Review redaction before broad log access.
- Passing generated media is intentionally public and cached for one year. New URLs bind UUID plus SHA-256, and the guard before every provider HTTP attempt recomputes the immutable stored byte digest and revalidates those bytes under the 5-MiB/JPEG/allowed-profile policy; the UUID-only route remains readable for already-published links. Migration 005 blocks media id/MIME/bytes/digest changes and every DELETE, creating a deliberate integrity/retention tradeoff. Model-supplied URLs/provenance, missing generation/hosting setup, fal URLs with credentials/fragments/nonstandard ports or redirects, oversized/non-image bytes, garbled text, identifiable people/features, readable plates/VIN/contact/customer documents, unsafe shop practices, material misrepresentation, QC errors, and malformed strict QC responses fail closed before approval. The same gate runs after every critic-requested image revision, and failed bytes are not intentionally hosted.
- Production rejects injected orchestration runner/image-resolver/publication-target seams and injected vision inspectors. These hooks are restricted to non-production offline validation; simulated dry-run scrubs the sensitive environment and forces test mode before configuration-bearing imports.
- No durable publish idempotency or recovery ledger exists.

## Sensitive tracked content

`config/approved-facts.json`, brand/agent/skill content, and the master prompt intentionally contain public business identity, service, address, phone, claims, and a public booking capability URL. These are executable content inputs, not credentials. Their continued publication and accuracy require business-owner review; do not mechanically redact them and silently change marketing behavior. Personal contact fallbacks and production platform numeric IDs do not belong in current setup documentation.

The credential-history pattern scan matched an embedded raster inside a brand SVG, not a provider credential, after manual triage. Pattern scans remain incomplete evidence.

## Secret handling

Keep database URLs, Anthropic/fal keys, Slack webhooks, Meta/Google tokens and secrets, console tokens, approval tokens/links, database exports, private analytics, and unpublished packages out of Git, chat, issues, screenshots, and fixtures. A SHA-256 token digest protects at-rest disclosure but does not make the URL safe to share. Base64, hashes of low-entropy secrets, and embedded JSON are not encryption.

If a credential is discovered in current files or history, revoke/rotate at the provider first, assess logs/use, then make a coordinated history-cleanup decision. Never rewrite history as an incidental documentation change.

## Private continuity register

Maintain outside Git: business/technical/social/approval/billing owners; Render team/services/domains/deploy controls; database owner/backup retention/restore evidence; every secret's storage location and last rotation; provider tenants/apps/pages/accounts/locations/scopes/test assets/revoke paths; Slack channel/webhook owners; Arcade counterpart; public site/booking ownership; incident contacts and vendor support routes. Record locations/owners, never values.

## Takeover

1. Obtain authorized source, Render, database backup, Slack, Anthropic, fal.ai, Meta, Google, Arcade, DNS/domain, and website/booking access.
2. Suspend scheduler/worker until platform identity, active platforms, autonomy phase, queue, approvals, and external posts are reconciled.
3. Rotate one boundary at a time, update all consuming services, and validate with offline/read-only checks. The API and Arcade currently share `CONSOLE_TOKEN`; update both before resuming.
4. Move persisted tokens to an encrypted/managed store before relying on long-term unattended operation.
5. Restore into isolation, then reconcile every external post/message/cost after the backup timestamp before resuming.

## Phase 0A rollout safety

`005_approval_integrity.sql` adds approval fields/constraints, append-only decisions, guarded status/revocation transitions, and media byte hashes/immutability. It deliberately revokes legacy pending/approved rows without a canonical hash/token hash, clears and constrains the plaintext-token column to NULL, and requires nonnull equal legacy/canonical copies whenever a bound Phase0A subject exists without backfilling unbound historical rows. It also backfills the digest of every media row. The runner holds one transaction, while transaction-local 10-second lock acquisition and five-minute per-statement deadlines fail visibly on unexpected contention/size instead of waiting indefinitely. This is safer than claiming old reviews authorized new bytes, but the table scan/locks and permanent media no-delete rule still need rollout review; do not auto-retry a timeout. Before any rollout, stop the legacy worker/scheduler as a hard gate because that binary ignores `revoked_at`; keep it stopped, back up PostgreSQL, drain/reject outstanding links, assess actual approval/media volume and locks, validate the migration in isolation, and use exactly one migration runner/process to apply migration 005. Start only the compatible API/worker/scheduler (their approval/media column/constraint/trigger probe otherwise fails) and require fresh review afterward. No production/shared migration or deployment was performed as part of the source change.
